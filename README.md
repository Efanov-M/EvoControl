# EvoControl
![image](assets/image.png)



**EvoControl** — веб-приложение для управления работой службы эвакуации транспортных средств.

Система предназначена для учёта автомобилей, водителей, эвакуаторов, диспетчеров, специализированных стоянок и нарядов-заданий. Основная цель разработки — автоматизация полного процесса эвакуации: от получения заявки диспетчером до выдачи автомобиля владельцу с сохранением истории операций.

**Статус проекта:** активная разработка.

**Назначение:** учебный проект, практическое изучение Django и формирование портфолио Python backend-разработчика.

## 1. О проекте

EvoControl создаётся как единая информационная система для эвакуационной службы.

В основе приложения лежат реальные рабочие процессы:

1. Диспетчер получает информацию о необходимости эвакуации.
2. Создаёт наряд-задание с указанием адреса, водителя и эвакуатора.
3. Водитель прибывает на место и регистрирует данные автомобиля.
4. Фиксируется основание изъятия, состояние автомобиля и фотографии.
5. Диспетчер специализированной стоянки подтверждает приём автомобиля.
6. При необходимости автомобиль перемещается между стоянками.
7. После выдачи автомобиля владельцу дело закрывается и сохраняется в архиве.

Проект предполагает сохранение истории операций и разграничение ответственности между участниками процесса.

Разработка ведётся самостоятельно с последовательным изучением архитектуры Django, ORM, реляционных баз данных, форм, валидации и организации серверной бизнес-логики.

## 3. Архитектура

Приложение построено на архитектуре Django MVT (Model–View–Template).

- **Model** — описывает сущности предметной области, их поля и связи.
- **View** — принимает HTTP-запросы, организует обработку данных и возвращает ответы.
- **Template** — формирует HTML-страницы с использованием Django Template Language.
- **Form / ModelForm** — обеспечивает получение, проверку и подготовку пользовательских данных.
- **ORM** — выполняет запросы к базе данных через модели Django.

Для сложных бизнес-операций планируется отдельный сервисный слой, отвечающий за согласованное изменение нескольких связанных сущностей, проверку правил и управление транзакциями.

## 4. Модель предметной области

В ходе разработки первоначальная структура базы данных была пересмотрена с учётом реального процесса эвакуации.

Главное архитектурное изменение — разделение автомобиля как самостоятельной сущности и конкретного случая его эвакуации.

### Vehicle

Модель `Vehicle` содержит идентификационные данные автомобиля:

- Государственный регистрационный номер.
- Марка.
- Модель.
- Цвет.

Один автомобиль может участвовать в нескольких случаях эвакуации.

### WorkOrder

Модель `WorkOrder` описывает наряд-задание, создаваемый диспетчером.

Основные данные:

- Адрес эвакуации.
- Назначенный водитель.
- Назначенный эвакуатор.
- Ответственный диспетчер.
- Статус выполнения.
- Дата и время создания.
- Комментарий.

Предусмотрены статусы:

| Статус | Значение |
|---|---|
| `created` | Создан |
| `assigned` | Назначен |
| `in_progress` | Выполняется |
| `completed` | Выполнен |
| `cancelled` | Отменён |

Наряд может существовать без зарегистрированного дела эвакуации, например при отмене задания или безрезультатном выезде.

### EvacuationCase

Модель `EvacuationCase` описывает отдельный случай эвакуации.

Содержит:

- Ссылку на автомобиль.
- Связь с нарядом-заданием.
- Основание изъятия.
- Признак участия автомобиля в ДТП.
- Текущую стоянку.
- Статус дела.
- Дату и время открытия.

Статусы дела: `active` и `closed`.

После выдачи автомобиля соответствующее дело должно переходить в закрытое состояние, сохраняя информацию для последующего просмотра.

### VehicleOperation

Модель `VehicleOperation` служит основой журнала событий.

Для отдельных типов операций предусмотрены специализированные модели:

- `EvacuationOperation` — оформление эвакуации.
- `ArrivalOperation` — приём автомобиля на стоянку.
- `TransferOperation` — перемещение между стоянками.
- `ReleaseOperation` — выдача автомобиля.

Каждая специализированная модель связана с общей записью операции через `OneToOneField`.

Такой подход разделяет общие свойства событий и информацию, характерную для конкретного действия.

### VehiclePhoto

Модель `VehiclePhoto` предназначена для хранения фотографий, относящихся к определённому делу эвакуации.

Фотографии связаны с `EvacuationCase`, а не непосредственно с `Vehicle`. Благодаря этому материалы разных эвакуаций одного автомобиля не смешиваются.

Интерфейс загрузки и просмотра фотографий находится в планах разработки.

## 5. Основной бизнес-процесс

Целевая последовательность действий в EvoControl:

```text
Диспетчер получает заявку
             |
             v
Создание наряда WorkOrder
             |
             v
Назначение водителя и эвакуатора
             |
             v
Водитель прибывает на место
             |
             v
Регистрация автомобиля
и оформление EvacuationCase
             |
             v
Фиксация эвакуации и фотографий
             |
             v
Приём автомобиля на стоянку
             |
             v
Хранение автомобиля
             |
             +------> Перемещение
             |             |
             |<------------+
             |
             v
Выдача автомобиля владельцу
             |
             v
Закрытие дела
             |
             v
Архив и история операций
```

Каждое действие должно выполняться с проверкой допустимости операции и корректным обновлением связанных данных.

При выполнении операций, изменяющих несколько записей базы данных, планируется использовать транзакции Django для обеспечения целостности данных.

## 6. Текущие функциональные возможности

### Справочники

Для основных справочных сущностей реализованы модели, формы и пользовательские страницы управления данными.

**Vehicles**

- Регистрация автомобилей.
- Просмотр списка.
- Поиск и сортировка.
- Просмотр и редактирование записей.
- Существующий CRUD требует адаптации к новой архитектуре эвакуаций.

**Fleet**

- Реестр эвакуаторов.
- Марка, модель, регистрационный номер.
- Тип эвакуатора.
- VIN.
- Признак активности.
- Страницы создания, просмотра, изменения и удаления.

**Drivers**

- Реестр водителей.
- ФИО и реквизиты водительского удостоверения.
- Страна выдачи удостоверения.
- Проверка формата данных.
- CRUD-интерфейс.

**Parking**

- Реестр специализированных стоянок.
- Название и адрес стоянки.
- Признак активности.
- CRUD-интерфейс.

**Dispatchers**

- Реестр диспетчеров.
- ФИО.
- Табельный номер.
- Место работы.
- Необязательная связь с учётной записью пользователя.
- Страницы списка, создания, детализации, редактирования и удаления.
- Поиск, сортировка и пагинация.

Отображение истории операций диспетчера будет подключено после реализации бизнес-логики операций.

### Наряды-задания — Tasks

Создано приложение `tasks`.

На текущем этапе реализованы или находятся в разработке:

- Модель наряда `WorkOrder`.
- Перечисление статусов `StatusOrder`.
- `WorkOrderForm`.
- Представление создания наряда.
- Представление списка с поиском, сортировкой и пагинацией.
- Представление детализации.
- Представление редактирования в процессе доработки.
- Регистрация нарядов в Django Admin.

Отмена, начало выполнения и завершение наряда пока не реализованы как полноценные бизнес-операции.

### Операции — Operations

Спроектирована структура моделей для жизненного цикла эвакуированного автомобиля.

Созданы модели дел эвакуации, специализированных операций и фотографий. Соответствующие миграции базы данных подготовлены и применены.

Пользовательские формы, обработчики и бизнес-логика выполнения операций находятся в разработке.

### Accounts

Создана собственная модель пользователя на основе `AbstractUser`.

Полноценная система аутентификации, ролей и разрешений будет реализована на следующих этапах.

## 7. Работа с базой данных

Для взаимодействия с SQLite используется Django ORM.

В проекте применяются:

- `ForeignKey` — отношения «один ко многим».
- `OneToOneField` — отношения «один к одному».
- `related_name` — обратные связи.
- `on_delete=PROTECT` — защита связанных записей от удаления.
- `on_delete=SET_NULL` — сохранение записи при удалении необязательной связи.
- `TextChoices` — перечисления допустимых значений.
- `QuerySet` — выборка, поиск, фильтрация и сортировка.
- `Q` — объединение условий поиска.
- `Paginator` — постраничный вывод результатов.
- Django Migrations — управление схемой БД.
- `ModelForm` — формы на основе моделей.

В перспективе предусмотрено изучение оптимизации запросов, индексов, ограничений целостности и транзакций.

## 8. Локальный запуск

### Требования

- Python, совместимый с используемой версией Django.
- Git.
- Виртуальное окружение Python.
- Установленные зависимости проекта.

### 1. Получение проекта

```bash
git clone https://github.com/Efanov-M/EvoControl.git
cd EvoControl
```

Если репозиторий имеет другой адрес, используйте актуальный URL.

### 2. Создание виртуального окружения

macOS / Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Windows:

```powershell
python -m venv .venv
.venv\Scripts\activate
```

### 3. Установка зависимостей

```bash
python -m pip install -r requirements.txt
```

Файл `requirements.txt` должен содержать актуальные зависимости Django-проекта, включая Django, Pillow и python-dotenv.

### 4. Конфигурация окружения

Создайте `.env` на основе `.env.example`.

Пример переменных:

```dotenv
DJANGO_SECRET_KEY=replace_with_your_secret_key
DJANGO_DEBUG=True
```

Для создания секретного ключа Django можно использовать:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Не публикуйте реальный `.env` или секретный ключ в Git.

### 5. Миграции

```bash
python manage.py migrate
```

### 6. Создание суперпользователя

```bash
python manage.py createsuperuser
```

### 7. Проверка и запуск

```bash
python manage.py check
python manage.py runserver
```

Сервер разработки по умолчанию запускается по адресу:

http://127.0.0.1:8000/

Доступные страницы зависят от подключённых URL-маршрутов. Django Admin доступна по `/admin/`.
